## 製品概要
### 背景(製品開発のきっかけ、課題等）
**誰の、どんな課題か**

対象は、AI(チャットや AI エージェント)と一緒に開発する人です。

AI でコードを書くのは速くなりました。でも人の仕事は消えず、AI が出した物を**読んで、確かめて、決める**側に移りました。速くなった分、こなす量も増えています。
- 開発者の 75% が「AI の出力を検証する責任が増えた」と答えています([Atlassian State of Developer Experience 2026](https://www.atlassian.com/teams/software-development/state-of-developer-experience-2026))。85% が「詰まる所が、書くことからレビューと検証に移った」と答えています([GitLab 2026](https://about.gitlab.com/press/releases/2026-06-23-gitlab-research-reveals-organizations-are-generating-ai-code-faster-than-they-can-control-it/))。どちらも自己申告の業界調査です
- AI を使うと 1 回の課題の負荷は下がります。それでも、確認の負荷が高いほど疲れが強くなっていた、という研究があります([Fan et al., CHI 2026](https://doi.org/10.1145/3772318.3791176))
- AI で仕事は減らず、むしろ密になる([HBR 2026-02](https://hbr.org/2026/02/ai-doesnt-reduce-work-it-intensifies-it))。複数の AI エージェントを監督する人が、頭の限界に追い込まれる([HBR 2026-03](https://hbr.org/2026/03/when-using-ai-leads-to-brain-fry))、という指摘も出ています

私たち自身も、AI を並列で動かして開発するうちに、確認と判断が詰まって頭がぐったりする経験をしてきました。AI エージェントが並列で仕事をすることで、人間も仕事の並列が求められるようになりました。

**今の休み方では足りない理由**

休憩の道具の多くは、時間で区切ります。ポモドーロ・テクニックは 25 分作業して 5 分休みます([公式](https://www.pomodorotechnique.com/))。[Stretchly](https://github.com/hovancik/stretchly) も時間で数えます。[Pausebar](https://pausebar.app/) は作業中かどうかを見て区切りまで待ちますが、何をしているかで負担を計算はしません。

でも、同じ 30 分でも、エラーと格闘した 30 分と、回答を読んでいただけの 30 分では、頭の使い方がまったく違います。時計はそれを区別できません。

**課題(1 文)**: 脳にかかる負担は作業の中身で変わるのに、休むタイミングは時間で決まっている。

私たちが目指すのは、**AI と一緒に、無理なく長く開発を続けられること**です。

### 製品説明（具体的な製品の説明）
**3 行で**
- **何を**: ChatGPT・Claude・Gemini の上で動く Chrome 拡張と、VS Code 拡張です
- **誰に**: AI と一緒に開発する人に
- **どう**: AI とのやり取りの中身から**脳への負担の目安を数値化**し、時間で区切って休むのではなく、**脳の負担に合わせてひといきつくタイミング**を提供します

**「器」とは**

ひといきでは、脳への負担の目安を、コップに水がたまるようなイメージの「**器**」で表します。
- 器は 0% から始まり、画面の右下に「計測中 ○%」と出ます(VS Code ではステータスバーに「ひといき ○%」)
- 作業をしている間、1 分ごとに、作業の中身(下の 5 つの要素)に応じた量がたまります。中身が重いほど速くたまります
- **80% を超えると「休憩が必要」**とみなし、区切りを待って休憩を提案します
- 休憩のタイマーが動いている間だけ、器は減ります。何もせずに放っておいても減りません(3 時間作業が無ければ、1 日の区切りとして 0 に戻します)
- パネルを開くと、どの要素がどれだけ器をためたか(内訳)が見られます

**どう考えて作ったか**

**① 知りたいこと**: いま、頭にどれだけ負担がかかっているか。カメラや脳波は使わずに、AI とのやり取りの記録から推定する「目安」にすると決めました。

**② 分解する**: AI と開発するときに頭を使う場面を、5 つに分けました。

| 要素 | 何を手がかりにするか | 考え・論文 | 計算での扱い |
|---|---|---|---|
| 読む量 | AI の回答の字数(語数) | 日本語は 1 分 653 字([小林・川嶋 2018](https://doi.org/10.3169/itej.72.J154))、英語は 1 分 238 語([Brysbaert 2019](https://doi.org/10.1016/j.jml.2019.104047))で読むとして、読み終えるまでの時間を出す | 読み残しがある間は 1 |
| 判断 | AI が「どちらにしますか」のように判断を求めた | AI の出した物を受けて決めるのも、確認の一部と考えた。確認の負荷が高いほど疲れが強い([Fan et al., CHI 2026](https://doi.org/10.1145/3772318.3791176)) | 会話を Claude API で分類して出来事を数える |
| 確認・検証 | エラーの貼り付け、「動かない」という報告 | 同上 | 貼り付けは手元の決まった型で、報告は Claude API で数える |
| 切替 | 会話の切替、別の話題への移動 | 切替には、予測できても残るコストがある([Rogers & Monsell 1995](https://doi.org/10.1037/0096-3445.124.2.207))。その大きさはルールの複雑さで変わる([Rubinstein et al. 2001](https://doi.org/10.1037/0096-1523.27.4.763)) | 「1 回 = ○秒」とは決めつけず、直近 5 分の件数を 2 件で頭打ちにした 0〜1 の値にする |
| 作業時間 | 作業している 1 分 | 時間も要素の 1 つ。ただし 5 つのうちの 1 つにとどめる | 作業中は 1 |

**③ 計算する**: 5 つを 0〜1 にそろえて、**等しい重みで平均**します。要素ごとの重みには研究の根拠がありません。根拠の無い係数をつけるより、そろえて足すだけで十分よく働く、という考え([Dawes 1979](https://doi.org/10.1037/0003-066x.34.7.571))に従いました。平均の値だけ、1 分ごとに器(上の説明)へたまります。

器は 2 層にしました。休むと回復する負担と、その日は残る負担です。これは、疲労を 2 層でたまる物として表したモデル([Müller et al. 2021, Nature Communications](https://doi.org/10.1038/s41467-021-24927-7))の形を借りています(元の研究は体の努力の実験です)。
```
1 分ごとの中身 e = (読む量 + 判断 + 確認・検証 + 切替 + 作業時間) ÷ 5      … 各 0〜1
作業中:   休むと回復する分 += 0.98 × 3.2 × e、その日は残る分 += 0.02 × 3.2 × e
休憩中:   休むと回復する分 −= 8 / 分
器 = 2 つの合計。80 を超えたら「休憩が必要」
```
この式で、いちばん重い作業なら 25 分、作業時間のほかに何も無いなら 125 分で 80 に届きます(どちらもテストで確かめた値、[`src/core/model.test.ts`](src/core/model.test.ts))。**同じ時間でも、作業の中身でたまる速さが約 5 倍変わります。**

**④ いつ声をかけるか**: 器が 80 を超えても、すぐには声をかけません。AI が生成している間、入力している間、長い回答を読んでいる間は待ちます。通知を作業の区切りまで遅らせると、苛立ちや反応の遅れが減る([Iqbal & Bailey, CHI 2008](https://doi.org/10.1145/1357054.1357070))。作業の途中の割り込みは、時間・ミス・不安を増やす([Bailey & Konstan 2006](https://doi.org/10.1016/j.chb.2005.12.009))。この 2 つを、休憩の提案に当てはめました。

**⑤ どう休むか**: 休憩の長さは 10〜15 分(器が 80 なら 10 分、100 なら 15 分)。厚生労働省の「連続作業は 1 時間以内、間に 10〜15 分の作業休止」([情報機器作業における労働衛生管理のためのガイドライン](https://www.mhlw.go.jp/content/000580827.pdf))に合わせました。**休憩は本人が始めます**。提案には「今 ○ 分休む」と「区切りがついたら休む」の 2 つのボタンがあります。休憩中は、円のタイマーとストレッチのピクトグラム、「戻ったら何をする?」の 1 行メモを出します(VS Code 版は休む前に聞きます)。戻ったら、メモと声かけを出し、「この休憩どうだった?」と聞きます。

**⑥ Hack Day で考えたこと: 中身をどこからでも取れるようにする**: ①〜③ の計算の式([`src/core/`](src/core/))は開会前に作りました。でも式だけでは、AI と開発する場所ごとに「いつ回答が終わったか」「いつ区切りか」が取れなければ動きません。Hack Day では、画面の作りが違う 3 つのサイトで回答の終わりを同じ決まりで取る方法(停止ボタンが消えたら、取れなければ回答の字数が 2.5 秒変わらなかったら)、エディタでの区切りの決め方(入力が 3 秒止まり、タスクもデバッグも動いていない)、API キーが無くても安全に分類を使える中継を考えて作りました(下の「独自技術」)。

- 判断と確認の一部は、本文の送信に同意すると共有中継を通じて会話を分類して取ります。自分の API キーで直接接続することもできます。同意前や通信できない時もローカルの手がかりで動きます(判断は「未計測」になります)
- **対応しているサイト**: ChatGPT(chatgpt.com。ログインして使う)・Claude(claude.ai)・Gemini(gemini.google.com)。Hack Day 中の記録で、3 サイトとも送信と回答が取れたことを確かめました。サイトごとの違いは画面の読み取り方だけで、[`src/content/sites.ts`](src/content/sites.ts) の定義を足せば広げられます。計算・画面・分類はどのサイトでも同じです
- **VS Code でも動きます**([`vscode/`](vscode/)): 同じ計算([`src/core/`](src/core/))を、エディタの出来事で動かします。読む量(まとまった挿入)・確認(ターミナルやタスクで動かしたテスト・ビルドの失敗)・ファイルの切替・作業時間でたまり、ステータスバーに「ひといき ○%」を出します。提案・休憩・おかえりは Chrome 版と同じ文と流れです。判断は VS Code では未計測で、器は Chrome 版と別々です(1 人に 1 つの器にまとめるのが次)

### 特長
#### 1. 脳への負担を数値化して、時間ではなく負担に合わせてひといき
ポモドーロのように時間で休むのではなく、脳への負担で休むタイミングを決めます。AI に判断を求められた回数や、エラーを貼った回数で、器のたまる速さが変わります。いちばん重い作業なら 25 分、作業時間のほかに何も無いなら 125 分で提案が出ます。同じ時間でも、中身でたまる速さが約 5 倍変わります。

#### 2. 作業を邪魔しない
AI が生成している間、入力している間、長い回答を読んでいる間は声をかけません。提案が出ても、休むかどうか・いつ休むかは本人が決めます。「区切りがついたら休む」を選ぶと、右下に開始ボタンが残り、好きな時に休憩を始められます。休憩中に × を押すと、画面の中央で「休憩を終えますか?」と確かめます。

#### 3. なぜ休もうと言われたかが分かる
計算は足し算なので、どの要素がどれだけ器をためたかを、そのまま理由として見せられます(例: 「確認・検証 38% / 読む量 27% / 作業時間 20%」「ひと息、休憩しませんか。確認や指示が続いています。」)。カメラは使いません。会話の本文は拡張に保存しません(記録は件数・文字数・時刻・操作だけ)。本文を分類に送るのは、最初に出る説明で同意した人だけです。

### 解決出来ること
| 課題 | ひといきの解き方 | 確かめたこと |
|---|---|---|
| 休むタイミングが時間で決まっていて、頭の使い方の違いを見ていない | 作業の中身(5 つの要素)で負担の目安をため、負担に合わせて提案する | 同じ計算で 25 分〜125 分、約 5 倍の差(テスト) |
| 休憩の通知が、作業の途中に割り込む | 生成中・入力中・読んでいる間は待ち、本人が始める | 区切りの判定のテスト。休憩の流れは本人の操作でしか始まらない |
| 確認や判断が続いていることに、自分では気づきにくい | 内訳と理由つきで声をかける | 内訳の計算と理由の文のテストで確認 |
| AI のキーが無いと試せない | API キー無しで分類を使える中継 | 下の記録(4 回中 4 回成功) |
| ブラウザの外(エディタ)での開発には効かない | 同じ計算を VS Code でも動かす | Marketplace に公開。VS Code の中で動かす自動テスト |

- **動いた記録**(Hack Day 中、2 人の Chrome の記録から): 10/24〜10/25 に、ChatGPT で 64 回、Claude で 5 回、Gemini で 8 回の送信を記録できました
- **API キー無しの中継での分類**(同じ記録から): 4 回中 4 回成功、平均 1.7 秒、モデルは Haiku 5.5 で **1 回 約 $0.0003**(実測)。自分のキーで Opus 5.5 を使った時(10 回中 10 回成功、平均 2.6 秒、1 回 約 $0.0065)の約 20 分の 1 です
- 集計は [`scripts/analyze-log.ts`](scripts/analyze-log.ts) で、設定画面から書き出した記録をそのまま読めます

### 今後の展望
- **人が増えたとき**: 分類は 1 回 約 $0.0003(実測)なので、1,000 回で約 $0.3 です。今の中継の全体の上限(1 日 1,000 回)は、試してもらうための守りです。配るときは上限を上げ、Chrome ウェブストアで出します
- **開発の現場に広げる**: VS Code では同じ計算が動きました。次は Claude Code・Codex の hooks です。承認待ちやテストの失敗まで取れるので、出来事の形を合わせれば同じ計算につなげられます
- **1 人に 1 つの器にする**: 今は Chrome と VS Code で器が別々です。頭は 1 つなので、まとめてためるのが次です
- **本人に合わせる**: 「役立った?」の答えや「あとで」を押した回数から、たまる速さを本人に合わせます

### 注力したこと（こだわり等）
* **根拠のある所と、仮置きの所を分けた**: 上の ②〜⑤ の表と式のとおり、値はできるだけ研究と公的な目安から取りました。要素ごとの重みだけは根拠が無いので、等重みにして、そう書いています
* **作りながら変えたこと**: 最初は、負担がたまると休憩タイマーを自動で始めるモードも用意していました。使ってみて、休むかどうかは本人が決めるほうがよいと考え、「本人が始める」形にまとめました(PR #1)。API キーが要る形から、誰でも試せるキー無しの形にも変えました(PR #13)
* **自分たちで組み立てた計算モデルで数値化する**: 脳の負担は、上の ②〜⑤ の計算モデルで数値化しています。LLM に点数はつけさせず、「判断を求めた箇所」「動かないという報告」「別の話題に移ったか」という**出来事**を抜き出す役だけを任せています
* **先行研究との位置づけ**: 作業ログから休憩の好機を予測する研究はあります([Kaur et al., CHI 2020](https://doi.org/10.1145/3313831.3376817))。ひといきは、AI との開発で増えた確認・判断の手がかりを、カメラなしで使います
* 表示は「ログから推定した作業の負担の目安」です。疲労を測っているわけではありません

## 開発技術
### 活用した技術
#### API・データ
* **Anthropic Claude API**: 会話の 1 往復ごとに、判断・確認・切替の**出来事だけ**を、構造化出力(JSON Schema。[公式](https://platform.claude.com/docs/en/build-with-claude/structured-outputs))で抜き出します。点数はつけさせず、脳の負担は自分たちで組み立てた計算モデルで数値化します。キー無し版の中継では、実測で 1 回 約 $0.0003・平均 1.7 秒だった Haiku 5.5 に固定しました
* **Cloudflare Workers + Durable Objects**: キー無し版の中継です。無料枠で 1 日 10 万リクエストまで動き、外への通信の待ちは CPU 時間に数えません([料金](https://developers.cloudflare.com/workers/platform/pricing/))。回数の上限は、同時に来ても正しく数えられる Durable Objects(SQLite)で数えます([公式](https://developers.cloudflare.com/durable-objects/))。ほかの候補(Vercel・Deno・Supabase)と比べて選びました
* 研究と公的な目安の値(上の「注力したこと」を参照)

#### フレームワーク・ライブラリ・モジュール
* **WXT**(Chrome 拡張のフレームワーク)、React、TypeScript: Manifest V3 の拡張を、3 つのサイト向けの content script と設定画面を 1 つのコードから作るため
* @anthropic-ai/sdk
* Vitest、happy-dom(計算と画面の読み取りのテスト)
* **VS Code Extension API**、esbuild、@vscode/test-electron: 計算([`src/core/`](src/core/))を画面から切り離しておいたので、エディタの出来事を同じ形に直すだけで載せられた。実際の VS Code を立ち上げて動かす自動テストつき

#### デバイス
* PC(Google Chrome、VS Code)

### 独自技術
#### ハッカソンで開発した独自機能・技術
**特に力を入れた所**(どれも Hack Day 中に作りました)

1. **API キー無しで、安全に分類を使える中継**(PR #13、commit `4ae9678`、[`proxy/src/handler.ts`](proxy/src/handler.ts)・[`proxy/src/quota.ts`](proxy/src/quota.ts)・[`src/shared/classification-service.ts`](src/shared/classification-service.ts))
   - 公開 URL は誰でも叩ける前提で作りました。中継が受けるのは本文 2 つと直前の作業名だけで、ほかの項目があれば断ります。モデル・出力の上限・指示文・JSON Schema は中継側で固定し、「誰でも使える Claude の入口」にならないようにしました
   - 回数の上限は、Durable Object(SQLite)で 1 インストールごと・全体の両方を、同時に来ても数え間違えない形で予約します。端末 ID は自己申告なので、最後の守りは全体の上限(1 日 1,000 回・1 分 30 回)と、Anthropic Console の月の金額の上限です。リダイレクトは失敗として扱い、キーや本文をほかの URL へ渡しません。本文はログにも残しません
   - 拡張の側は、最初に説明を出して同意を取ってから送ります。同意を取り消したり設定を変えたりすると、途中の通信も止め、古い分類の結果は使いません
2. **画面の作りが違っても、送信と回答の終わりを取りこぼさない観測係**(PR #2・#20、commit `356a159`・`488b054`、[`src/content/observer.ts`](src/content/observer.ts)・[`src/content/sites.ts`](src/content/sites.ts))
   - サイトごとの違いは読み取り方の定義だけにして、ChatGPT・Claude・Gemini で同じ観測係を使います
   - 回答の終わりは「停止ボタンが消えた」で決め、停止ボタンが取れない時は「**最後の回答の字数が 2.5 秒変わらない**」で決めます。送信した時点の最後の回答を覚えておき、それとは別の回答のときだけ終わりとみなすので、前の回答を新しい回答と取り違えません。送信の取りこぼしは、吹き出しが 1 つ増えたことから補います
   - 実際の画面で取りこぼした場面(前の回答が残っている会話で送る、吹き出しが遅れて出る など)は、テストにして直しました
3. **同じ計算を、VS Code の出来事で動かす**(PR #5、commit `40f78c0`、[`vscode/src/tracker.ts`](vscode/src/tracker.ts))
   - 同じ計算([`src/core/`](src/core/))を使い(読む量の上限だけエディタ向けに変えて)、エディタの出来事を同じ形に直して入れます。まとまった挿入は読む量、ターミナルやタスクの失敗は確認・検証、ファイルの切替は切替です
   - 区切りの判定もエディタ向けに作りました。入力が 3 秒止まり、終わる種類のタスクもデバッグも動いておらず、窓が前にある時だけ声をかけます
   - [Marketplace に公開](https://marketplace.visualstudio.com/items?itemName=koubeyapurin.hitoiki)し、「ひといき」と検索して入れられます
